# capstone-traffic-generator

Simulates a realistic user population hitting `startup-capstone-api` around the
clock, so DevOps has real load to monitor, Security has real auth events to
investigate, and Data has a real dataset instead of a static CSV.

## Run locally

```bash
npm install # no external deps currently, but keeps the workflow consistent
TARGET_URL=http://localhost:3000 node generator.js
```

## Run on the EC2 host (recommended: systemd, not a foreground terminal)

Create `/etc/systemd/system/capstone-traffic.service`:

```ini
[Unit]
Description=Capstone Traffic Generator
After=network.target docker.service

[Service]
Type=simple
Environment=TARGET_URL=http://localhost:3000
WorkingDirectory=/opt/capstone/traffic-generator
ExecStart=/usr/bin/node generator.js
Restart=always
RestartSec=5
User=ec2-user

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now capstone-traffic
sudo journalctl -u capstone-traffic -f   # watch it running
```

## Tuning

All rates, weights, and the hourly traffic curve live in `config.js`. Turn
`BASE_REQUESTS_PER_TICK` down for a quieter classroom demo, or up if you want
CloudWatch alarms to trip faster during a live session.

## What it produces (for instructors)

- **Baseline traffic**: browsing, logins, orders — varies by hour to mimic a
  real SaaS usage curve.
- **Failed logins**: ~35% of simulated logins are intentionally invalid,
  spread across normal-looking IPs — background noise for the Security track
  to filter past.
- **Brute-force bursts**: ~2x/day, 25 rapid failed `admin` login attempts from
  one fixed IP (`config.SUSPICIOUS_IP`) — the "attack" students should detect.
- **Admin endpoint probes**: occasional low-volume hits to `/api/admin/stats`
  from the same suspicious IP — simulates recon against the exposed endpoint.
- **5xx errors**: generated by the API itself (~3% of order creations) — no
  action needed here, just something for dashboards/alarms to catch.
